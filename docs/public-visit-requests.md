# Public physician visit requests

## Registered physician routing

Active doctors provisioned by a center administrator or approved through staff onboarding automatically have `registered-{userId}` public profiles. Database triggers synchronize their registered specialty, display name and public center address/phone within the same transaction. Personal signup mobile numbers are never published as a fallback. Existing active doctors are backfilled; imported real-world profiles are never linked by name or overwritten. An existing explicitly linked imported profile is preserved rather than creating a second link. Directory responses include `profileOrigin: registered|imported`; registered profiles have `sourceUrl:null` and the actual `accountId`. Inactive doctors or centers are excluded from directory results and cannot receive new requests.

Patients select this actual registered profile to deliver their request to the same doctor's authenticated queue. Approval or rejection appears in the patient's request history. Confirmation serializes decisions for that doctor, rejects times inside an existing active appointment, and enforces a database unique confirmed start time per profile. This request workflow does not allocate appointment inventory or infer appointment duration; external physician calendars remain separate.

Every published directory physician can receive a patient request stored in `public_visit_requests`. This is a pending request, not a reserved appointment slot. Public physicians are not automatically registered service providers: requests do not trigger an external notification, payment, video session or booking-calendar integration.

`POST /api/practitioners/:id/visit-requests` requires an authenticated patient and valid CSRF header. Body: `{patientName,phone,preferredDate,preferredTime,visitType,reason,consent:true}`. Dates are ISO Gregorian `YYYY-MM-DD`; time is `HH:mm` interpreted in Tehran (+03:30). Iranian phone and Persian/Arabic digits normalize on the server. Proposed time must be future and at most 90 days away. Visit type is `in_person` or `online`; reason is optional and limited to 1000 characters. Consent version, audit record and request are persisted atomically. Duplicate pending requests from the same patient for the same physician and day return 409.

Response: `{visitRequest:{id,reference,status,practitionerId,practitionerName,patientId,patientName,phone,preferredDate,preferredTime,visitType,reason,createdAt,updatedAt}}`. New status is always `pending`. `reference` is a random tracking code, not a bearer access credential.

`GET /api/visit-requests` returns `{visitRequests}` restricted to the current patient, or to an authenticated active doctor explicitly linked to that directory profile through `account_id`. Other roles cannot access patient requests. `PATCH /api/visit-requests/:id {status:cancelled}` lets the owner cancel a pending or confirmed request. Only the actual linked active doctor can change a pending request to `confirmed` or `rejected`; unlinked directory physicians cannot confirm. Cross-user requests return 404. Transitions are transactional with row locks and append-only audit events. Existing appointment tables and calendars are unchanged.
