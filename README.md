# شمساز | Shamsaz

سامانهٔ مدیریت گردش‌کار مراقبت سلامت زنان با React، Express و PostgreSQL. این مخزن شامل رابط عمومی، فضای کار پنج نقش، احراز هویت واقعی و ثبت پایدار اطلاعات است.

## راه‌اندازی محلی

پیش‌نیازها: Node.js 24 یا بالاتر و Docker Compose با سرویس Docker فعال.

1. `npm install`
2. فایل `.env.example` را به `.env` کپی کنید؛ رمز PostgreSQL را بسازید و همان مقدار را در `DATABASE_URL` قرار دهید.
3. `npm run db:up`
4. `npm run db:migrate`
5. `npm run dev`

رابط و API روی [localhost:3001](http://localhost:3001) اجرا می‌شوند. PostgreSQL فقط روی `127.0.0.1:5433` قابل دسترسی است. داده‌ها در volume مستقل Docker ذخیره می‌شوند؛ توقف سرور برنامه اطلاعات را پاک نمی‌کند. پورت برنامه با `PORT` قابل تنظیم است.

## ساختار

تنظیمات انتشار روی پلن رایگان Render در `render.yaml` قرار دارد و PostgreSQL باید از پروژه مستقل Neon تأمین شود. نام درخواستی سرویس `shamsaz` است؛ نام و آدرس نهایی تا ساخته‌شدن سرویس رزرو نشده‌اند. برای انتشار کامل، حساب‌های Render، Neon و مخزن GitHub باید متصل باشند. `DATABASE_URL` با SSL و `APP_ORIGIN` برابر آدرس HTTPS واقعی سرویس، در محیط امن هاست تنظیم می‌شوند. پلن رایگان Render پس از عدم فعالیت متوقف می‌شود و راه‌اندازی مجدد می‌تواند تأخیر داشته باشد؛ پایگاه‌داده رایگان Render پس از ۳۰ روز منقضی می‌شود، بنابراین فایل انتشار از آن استفاده نمی‌کند. منابع: [Render Free](https://render.com/docs/free)، [Neon Free](https://neon.com/blog/neon-free-plan-1-gb-per-project).

شروع سرویس، snapshot شامل ۴۴ پروفایل عمومی پزشکان و عکس‌ها را به‌صورت idempotent وارد می‌کند؛ حساب آزمایشی، نشست، اطلاعات بیمار و پرونده‌های سلامت منتقل نمی‌شوند. تولید snapshot عمومی با `npm run directory:snapshot` فقط از دیتابیس محلی مجاز است. داده‌های موجود و اتصال حساب پزشک با `directory:restore` بازنویسی نمی‌شوند. ایجاد اولین مدیر و مرکز واقعی با دستور مستند `db:bootstrap-admin` و متغیرهای امن انجام می‌شود. بازیابی رمز در production به SMTP نیاز دارد و صندوق توسعه غیرفعال است. `npm run build` و سپس `npm run test:production` اجرای production را روی دیتابیس موقت خالی بررسی می‌کنند؛ این آزمون انتشار اینترنتی محسوب نمی‌شود.

## نقش‌ها و دادهٔ آزمایشی

ثبت‌نام بیمار بلافاصله حساب فعال می‌سازد. درخواست ثبت‌نام پزشک و کارشناس رجیستری تا بررسی مدیر مرکز در انتظار می‌ماند. فرم‌ها شامل اعتبارسنجی، تاریخ تولد شمسی و رضایت هستند؛ ورود با ایمیل یا موبایل انجام می‌شود. بازیابی رمز در توسعه صندوق محلی و در استقرار SMTP دارد. جزئیات در [احراز هویت](docs/authentication.md) است. پذیرش بیمار در مرکز با رضایت ثبت می‌شود. ناظر ملی دادهٔ تجمیعی دریافت می‌کند؛ تغییر نقش یا اختصاص مرکز از فرم پروفایل ممکن نیست.

برای فعال‌سازی دادهٔ مصنوعی توسعه، `ENABLE_DEMO_SEED=true` و `DEMO_PASSWORD` با حداقل ۱۲ کاراکتر تنظیم کنید. حساب‌ها: `patient@shamsaz.local`، `doctor@shamsaz.local`، `registry@shamsaz.local`، `admin@shamsaz.local` و `supervisor@shamsaz.local`. رمز در محیط محلی تعیین می‌شود و در مخزن قرار ندارد. seed در production ممنوع است؛ رمز حساب موجود با اجرای مجدد تغییر نمی‌کند.

## بررسی و انتشار

```text
npm run typecheck
npm test
npm run test:ui
npm run test:directory
npm run test:booking
npm run test:patient-doctor
npm run test:screening
npm run test:banners
npm run test:carousel
npm run test:centers
npm run build
npm start
```

`npm start` از فایل‌های ساخته‌شدهٔ `dist` استفاده می‌کند و Vite توسعه را اجرا نمی‌کند. در production باید `ENABLE_DEMO_SEED=false`، `DATABASE_URL` امن و `APP_ORIGIN` مطابق دامنهٔ HTTPS تنظیم شوند. نشست production به cookie امن نیاز دارد. مهاجرت‌ها هنگام شروع هم اجرا می‌شوند؛ در استقرار واقعی، اجرای migration را با نقش جداگانه و قبل از شروع برنامه مدیریت کنید.

برای ایجاد اولین مدیر مرکز در دیتابیس خالی، متغیرهای `BOOTSTRAP_ADMIN_EMAIL`، `BOOTSTRAP_ADMIN_PASSWORD`، `BOOTSTRAP_ADMIN_NAME` و `BOOTSTRAP_ORGANIZATION_NAME` را در محیط امن تنظیم و `npm run db:bootstrap-admin` را اجرا کنید. این ابزار نقش یا رمز حساب موجود را تغییر نمی‌دهد و اطلاعات ورود را چاپ نمی‌کند. حساب ناظر ملی از این ابزار ساخته نمی‌شود.

`npm test` روی PostgreSQL محلی یک دیتابیس موقت مستقل می‌سازد و پس از تست آن را حذف می‌کند؛ رکوردهای توسعه تغییر نمی‌کنند. برای CI دارای نقش محدود، `TEST_DATABASE_URL` را به یک دیتابیس اختصاصی تست بدهید؛ این حالت دیتابیس را خودکار حذف نمی‌کند. اجرای مستقیم فایل تست از Node از دیتابیس تنظیم‌شده استفاده می‌کند و برای استفادهٔ معمول توصیه نمی‌شود.

## محدودهٔ فعلی

«غربالگری هوشمند» دارای مسیر پنج‌مرحله‌ای اطلاعات سلامت، علائم هشدار، آزمایش‌های قبلی، بازبینی و رضایت، و گزارش اقدام بعدی است. برنامه‌های پستان، دهانه رحم، تخمدان و آندومتر با منابع مرجع و محدودیت‌هایشان نمایش داده می‌شوند. نتیجه در سرور با قواعد شفاف تولید و در PostgreSQL همراه نسخه و رضایت ذخیره می‌شود؛ درصد احتمال سرطان یا تشخیص هوش مصنوعی ارائه نمی‌شود. تاریخچهٔ شخصی، دریافت JSON، چاپ گزارش، راهنمای مراجعه و پرسش‌های متداول فعال‌اند. تست `test:screening` مسیر مرورگری، خطای ذخیره و تلاش مجدد، ورود مجدد و ماندگاری گزارش، هشدار فوری، خروجی چاپی و چهار عرض نمایش را در دیتابیس موقت مستقل بررسی می‌کند؛ مدارک در `.local/ui-qa/screening` هستند.

تمام صفحات فعال و داشبوردهای نقش‌ها بنر تصویری اختصاصی دارند. [طراحی بنرها، فایل‌ها و پرامپت‌ها](docs/banner-assets.md) شامل نگاشت مسیرها، کنترل حرکت و روش بررسی موبایل است.

فهرست پزشکان تهران از `data/tehran-practitioners.json` با `npm run directory:import` وارد PostgreSQL می‌شود. این بانک مستقل از حساب پزشک است و منبع اطلاعات و عکس را نگه می‌دارد؛ ثبت پروفایل عمومی به معنای عضویت پزشک در سامانه یا فعال‌بودن نوبت‌دهی نیست. تصویر دریافت‌شده به‌صورت `bytea` ذخیره می‌شود. [مستندات فهرست پزشکان](docs/practitioner-directory.md).

زیر هر پزشک دکمهٔ رزرو ویزیت قرار دارد. درخواست بیمار با زمان پیشنهادی و رضایت در PostgreSQL ذخیره می‌شود، کد پیگیری می‌گیرد و در داشبورد قابل مشاهده و لغو است. برای پزشکان عمومیِ فاقد حساب متصل، هماهنگی مطب برای تأیید زمان لازم است. تست `test:booking` مسیر انتخاب پزشک، ورود و بازگشت، ثبت و پیگیری پس از تازه‌سازی و لغو را در دیتابیس موقت مستقل بررسی می‌کند.

پزشک عضو فعال پس از تأیید حساب، پروفایل متصل در فهرست دارد. درخواست ثبت‌شده برای این پروفایل در بخش «درخواست‌های ویزیت بیماران» پنل همان پزشک نمایش داده می‌شود؛ تأیید یا رد پزشک نیز در تاریخچهٔ بیمار دیده می‌شود. تست `test:patient-doctor` ثبت‌نام بیمار، خروج و ورود مجدد، انتخاب پزشک، ثبت درخواست، مشاهده و تأیید در پنل همان پزشک و مشاهدهٔ نتیجه در پنل بیمار را در مرورگر و PostgreSQL بررسی می‌کند. دسترسی پزشک دیگر نیز در دیتابیس موقت آزموده می‌شود. تصاویر و گزارش در `.local/ui-qa/patient-doctor-flow/isolated` ذخیره می‌شوند.

اجرای اختیاری همین آزمون با `LIVE_BOOKING_QA=true` روی پلتفرم محلی فعال، یک بیمار مصنوعی و درخواست تأییدشده در دیتابیس توسعه باقی می‌گذارد؛ خروجی آن در `.local/ui-qa/patient-doctor-flow/live` است. اجرای پیش‌فرض از دیتابیس موقت مستقل استفاده می‌کند. تأیید درخواست به معنی تخصیص موجودی تقویم نوبت‌ها نیست؛ جزئیات در [گردش درخواست ویزیت](docs/public-visit-requests.md) آمده است.

ثبت نوبت، علائم، پروفایل، رجیستری، مستندسازی پزشک و مدیریت مرکز از مسیر API انجام می‌شود. یادداشت و نسخهٔ پزشک پیش‌نویس هستند. اتصال واقعی بیمه، پیامک، تماس تصویری، ذخیرهٔ فایل پزشکی و مدل بالینی اعتبارسنجی‌شده هنوز پیاده‌سازی نشده است. وجود جدول یا نمونهٔ رابط به معنای فعال‌بودن خدمت نیست. این نسخه برای توسعه و بررسی گردش‌کار با اطلاعات مصنوعی است.
